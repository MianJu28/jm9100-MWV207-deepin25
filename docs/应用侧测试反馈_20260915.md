## 5. 黑窗根因定位结论（反馈清单 §6）

> 这是本次最值得驱动侧记录的一条：purelive 历史上的黑窗，**根因是窗口未被 KWin 接管（`managed=0`，始终停留在占位 64×64 或自建 1400×820 但不受合成、不可见），而不是 EGL visual / 黑窗渲染失败。**

- 证据：窗口属性追踪显示，从 `t=0.27` 起窗口即 `managed=0`，持续 30s 不接受窗口管理 → 不被合成、不可见；"黑窗"实为未合成。
- 与清单 §4.1 一致：因 EGL 在全部 visual 上都能建面，所以"黑"不发生在 EGL 层，而发生在**窗口管理/合成**层。
- 应用侧修复（`linux/my_application.cc`）：首帧后若检测到窗口仍 `managed=0`，则重设 visual 并触发 GTK 重绘，使其被 KWin 正常接管。当前 3 次启动（含首次冷启动）均 `IsViewable` + `_NET_WM_STATE_FOCUSED`，`RMSE≈0.05`，黑窗已消除。
- 建议驱动侧/清单维护：把清单 §6「purelive 的 `Could not wrap embedder supplied frame-buffer`」从"待定位"改为"**已解决（应用侧渲染目标传递 + WM 接管自愈）**"；并把黑窗主因从 EGL 层明确划到窗口管理/合成层（与 §4.1 一致，不再回查 EGL visual）。

## 6. 应用侧已做的配套改动（供驱动侧知晓，无需系统侧处理）

### §3.1 GL vendor 变量：应用在代码内显式 pin

- 新增 `applyHardwareGlEnvironment()`（`linux/jm9100_gl.cc`）：在 `jm9100_gl_prepare_environment` 内、**探针 fork 之前**就 `setenv("__GLX_VENDOR_LIBRARY_NAME","mwv207",1)`，并 pin EGL vendor 指向 `/usr/share/glvnd/egl_vendor.d/10_mwv207.json`。
- **为什么要放在探针之前**（本轮踩坑）：初版把 pin 放在探针成功之后，但探针 child 是之前 fork 的，变量未 pin 回去 → 探针在 mesa/llvmpipe 下跑通过、误标"硬件可用"，窗口实际用 llvmpipe。改为探针前 pin 后，探针验证的是真实 `Jingjia` 硬件栈；若硬件真不可用，探针失败仍回落 `applySoftwareGlEnvironment()`（mesa/llvmpipe）。
- 验证（模拟 `pkexec` 丢变量）：

  ```
  正常桌面启动（继承 __GLX_VENDOR_LIBRARY_NAME=mwv207）：
    jm9100: GPU GL stack enabled (visual 0x6c, renderer Jingjia JM9100)
  env -u __GLX_VENDOR_LIBRARY_NAME -u __EGL_VENDOR_LIBRARY_FILENAMES 启动（模拟 pkexec 剥离）：
    修复前：renderer = llvmpipe (LLVM 17.0.6)   ← 静默用软渲染且自认“硬件”
    修复后：renderer = Jingjia JM9100，窗口 RMSE=0.00544898（可见）
  ```

  结论：即便 GL 变量被 `pkexec`/桌面图标启动剥离，应用也自行 pin 回 `mwv207`，**不再白/黑屏**（对应清单 §3.5）。

### §3.3 VA-API 零拷贝：应用内进程拦截（等价“应用级”方案）

- `linux/jm9100_gl.cc` 的 `eglGetProcAddress` 拦截器：仅当 `GL_VENDOR` 含 `Jingjia` 且 OES 入口存在时，把 `glEGLImageTargetTexStorageEXT` / `glEGLImageTargetTextureStorageEXT` 重定向到 `glEGLImageTargetTexture2DOES`，同时拦截 `getProcAddress`（覆盖 epoxy/glad 绕过动态链接器的情形）。等价于清单 §3.3 的 `mpv_dmabuf_oes_image.patch`，但**不修改 libmpv 二进制**、升级后无需重打补丁。

## 8. 给驱动侧的 actionable 反馈

1. **清单 §6 黑窗归因更新**：purelive 黑窗根因 = 窗口未被 KWin 接管（`managed=0`），非 EGL/visual；与 §4.1 一致，建议把「`Could not wrap embedder supplied frame-buffer`」标为已解决。
2. **§3.1 系统侧双保险建议保留**：应用侧已兜底，但清单 §3.1 要求的 `/etc/environment` PAM 双写仍建议确认覆盖 `pkexec` 场景（应用侧兜底作为第二道保险已验证有效）。
3. **§3.3 兼容层可选**：purelive 走应用内等价拦截，不依赖系统 `libjm_gl_compat.so`；若其它应用（mpv 独立进程）仍需零拷贝，仍按清单 D1–D4 安装系统兼容层。
4. **未测项**：B3（≥10min 连续）、F1–F3（端到端播放）、E2、G 系列——建议后续用播放器专项 + 真 `pkexec` 场景补验。

## 9. 驱动侧响应（2026-09-15）

1. **黑窗归因确认并已闭环**：与清单 §4.1 一致，`egl_force_visual` 实测 90/90 visual 均可建面渲染，
   EGL 不是黑窗根因。应用侧反馈的"窗口未被 KWin 接管（`managed=0`）"是更靠后的真因，已由应用侧
   WM 接管自愈解决；清单 §6 已将 purelive 的 `Could not wrap embedder supplied frame-buffer` 标为「已解决」。
2. **`glEGLImageTargetTexStorageEXT` 反编译结论（支撑 §3.3 兼容层）**：原生驱动**未实现**该扩展——
   `jmgpu_dri.so` 内无此符号/字符串，glvnd 用空桩应答（`dladdr` 落在 `libGLdispatch.so.0`），故纹理恒全零；
   原生栈也不广告 `GL_EXT_EGL_image_storage`（实测 `advertised = NO`）。证实 §3.8「无法小补丁修复」成立。
3. **系统兼容层已安装**（2026-09-15）：`/usr/lib/aarch64-linux-gnu/libjm_gl_compat.so` 已就位；
   装后 `glxinfo | grep GL_EXT_EGL_image_storage` 可见该扩展。standalone mpv/Chromium 等走 storage 路径的
   客户端，用 `LD_PRELOAD=.../libjm_gl_compat.so LIBVA_DRIVER_NAME=jmgpu` 即可零拷贝直通（无需改应用/打补丁）。
4. **对厂商的真正诉求**：请实现 `glEGLImageTargetTexStorageEXT`（复用 OES 的 dmabuf 绑定即可），实现后
   兼容层可退役。另 GL 客户端 vsync 不真正节流、gl2 合成 1–11fps 两项仍属厂商合成实现缺陷（清单 §7）。
5. **建议补验项**（呼应反馈 §8-4）：用真实 `pkexec` 场景 + 播放器端到端硬解做一轮专项，闭合 F1–F3 / E1。
