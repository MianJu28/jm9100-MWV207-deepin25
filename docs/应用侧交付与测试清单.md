## 0. 结论摘要（先看这三条）

1. **系统层已就绪**：专有 X 驱动（`mwv207_drv.so` ABI 补丁版）正常工作；硬件 GL 可用
   （`glxgears` 默认开垂直同步即 **14,583 / 15,643 FPS**）；VA-API 硬解 + dmabuf 零拷贝直通可用；
   桌面合成 **60fps 满帧**。
2. **应用侧无需任何改动**即可用硬件 GL/EGL，**也无需任何 `LD_PRELOAD` / 环境变量**即得
   VA-API 零拷贝直通：2026-09-16 起 `GL_EXT_EGL_image_storage` 已在厂商库层原生补齐
   （§2 #8 / §3.3），原先"必须用兼容层或给应用打补丁"的限制**已取消**。
3. **本轮推翻了一条长期错误归因**：此前认为「厂商 EGL 的 config 只覆盖 1 个 visual，导致一切
   EGL 建窗口 surface 的客户端黑窗」。实测**厂商 EGL 在屏幕全部 90 个 visual 上都能建窗口表面
   并完成渲染/交换**（§4.1）。因此：**应用若仍出现黑窗，请按 §6 重新定位，不要再归因到 EGL visual。**

## 3. 应用侧需要知道的三件事

### 3.1 GL vendor 变量是硬依赖（别丢）

景美 GL 依赖环境变量 `__GLX_VENDOR_LIBRARY_NAME=mwv207`。它必须同时存在于：

- `/etc/profile.d/mwv207_glvnd.sh` —— 登录 shell / 桌面会话应用；
- `/etc/environment` —— **PAM 会话**（`pkexec` / `su` / `login` / `sshd` / `lightdm` / `cron`）。

**为什么**：任何“自我提权”的应用（`pkexec` 会清空并重建环境）若拿不到该变量，glvnd 会取 X server
通告的 vendor 名（Xorg 默认 `mesa`）→ 加载 `libGLX_mesa.so.0` → Mesa 对 `0731:9100` 无驱动 →
WebKit WebProcess 直接死亡 → **白屏**（§3.5 有完整复现与对照）。

**给应用侧的建议**：如果你的应用会在提权后重新绘制窗口，请**不要**依赖 shell 环境传递，改为在代码里
显式设置（或确保走 `/etc/environment` 这条 PAM 链路）。

> 复现陷阱：**不能用 `sudo <app>` 复现/验证**该问题 —— `sudo` 的 PAM 栈不含 `pam_env`，
> 自带变量，画面正常，会得出“没问题”的错误结论。必须走 `pkexec`（桌面图标启动）。

### 3.2 垂直同步语义（预期内，不是 bug）

内核修复（§2 #3）后，**vblank 等待不再超时**，但厂商 GL 的 vsync **仍未真正实现节流**：
开垂直同步的 GL 应用实测仍是 1.4 万 FPS 量级，而不是 60。应用侧**不要**把“开了 vsync 但帧率不受限”
当成本次适配的缺陷上报（已作为厂商缺陷另行反馈，见 §8.1）。

### 3.3 VA-API 零拷贝直通：两种接入方式（二选一）

背景：景美桌面 GL 声明了 `GL_OES_EGL_image`（`glEGLImageTargetTexture2DOES` 真能用），但**未声明**
`GL_EXT_EGL_image_storage`，且 `glEGLImageTargetTexStorageEXT` **原生驱动根本未实现**——
经反编译确认：厂商 `jmgpu_dri.so` 内无此函数符号/字符串，glvnd 用一个**空桩**应答，调用它得到的
纹理恒全零。结论与 §3.8「无法小补丁修复」一致。详见 §4.4。
后果：走 storage 路径的客户端（mpv `vaapi_gl_mapper`、Chromium 等）会主动拒绝 dmabuf 零拷贝
（回落 `vaapi-copy` 或软解）；在 Mesa/llvmpipe 上更会**静默产出全零帧（绿屏）**。

| 方式 | 做法 | 适用 |
|---|---|---|
| **原生（最优，2026-09-16 新增）** | `sudo ./install_gl_storage.sh`（给三个厂商库打字节补丁，见 §2 #8 / README §9） | **首选**：任何应用、无需任何环境变量或 `LD_PRELOAD`；驱动升级后需重打 |
| 系统级（兼容层） | `./build_gl_compat.sh install`，再以 `LD_PRELOAD=/usr/lib/aarch64-linux-gnu/libjm_gl_compat.so` 启动应用 | 原生补丁未安装时的兜底；**未打补丁的任何应用**都能进入 direct |
| 应用级 | 给应用打 `mpv_dmabuf_oes_image.patch`（desktop GL 改走 `glEGLImageTargetTexture2DOES`）后重编 | 只修单个应用；升级后需重新应用 |

兼容层特性：广告 `GL_EXT_EGL_image_storage`（覆盖 `glGetString` / `glGetStringi` / `GL_NUM_EXTENSIONS`
三条路径）；把 storage 入口重定向到 OES 入口；**同时拦截 `getProcAddress`**（epoxy/glad/GLEW 绕过动态
链接器符号表，只做符号插入抓不到）；仅当 `GL_VENDOR` 含 `Jingjia` 且 OES 入口真实存在时介入，
其它 GL 栈原样透传。开关：`JMGPU_GL_COMPAT=0` 关闭，`JMGPU_GL_COMPAT_DEBUG=1` 打日志。

> **当前状态（2026-09-16 更新）：兼容层已从系统卸载，且不再需要。**
> 原生补丁（§2 #8）已在厂商库层补齐 `GL_EXT_EGL_image_storage`，应用侧**无需 `LD_PRELOAD`**：
> `glxinfo | grep GL_EXT_EGL_image_storage` 在原生栈下即可看到该扩展。
> 复验（无 `LD_PRELOAD`、系统原版 mpv）：`Using EGL dmabuf interop via GL_EXT_EGL_image_storage`，
> `test_passthrough.sh` 判定直通正常。
> 兼容层源码/脚本（`jm_gl_compat.c` / `build_gl_compat.sh` / `test_gl_compat.sh`）仍保留在仓库，
> 作为"原生补丁未安装（例如驱动升级后尚未重打）"时的兜底：`./build_gl_compat.sh install` 即可。

判定零拷贝是否真的生效：应用日志应出现
`Using EGL dmabuf interop via GL_EXT_EGL_image_storage`，且画面不是“全零绿屏”
（用 `ppm_stats.py` 判色，绿屏特征为绿色占比 100%）。

## 4. 本轮新发现（2026-09-15「反编译专项」）

### 4.1 更正：厂商 EGL 的 visual 覆盖不是黑窗根因（原 §3.7 结论作废）

**原结论**（README §3.7）：景美 EGL 的 40 个 config 只覆盖 `0x21` 一个 visual，其余 89 个 visual
无 config → `eglCreateWindowSurface` 必然失败 → 黑窗。

**新实验**：新探针 `egl_force_visual.c`（本仓库）**无视** config 报告的 visual，直接拿 `config[0]`
到屏幕**全部 90 个 visual** 上建 EGL window surface，并真正执行 `eglMakeCurrent` + `glClear` +
`eglSwapBuffers`：

```
厂商 EGL：共 40 个 config，统一使用 config[0]（其 EGL_NATIVE_VISUAL_ID=0x21）
visual   depth class       surface  eglGetError  渲染(glClear+swap)
  0x21     24    TrueColor   OK       -            OK
  0x22     24    DirectColor OK       -            OK
  0x6c     32    TrueColor   OK       -            OK     ← Flutter/GTK 偏好的 32 位 ARGB
  ...（其余 87 个同样 OK）...
小结: visual 总数 90，surface 建立失败 0，可完整渲染 90
```

**结论**：`eglCreateWindowSurface` **不做 config↔visual 匹配校验**，任何 visual 都能建成 surface
并正常渲染/交换。`EGL_NATIVE_VISUAL_ID` 的“显示级返回 `0x21`”只是**查询语义的简化**，不是能力限制。

**为什么之前会误判**：`jm_egl_visual_probe` 的输出「无匹配 config，引擎必然失败」是**探针自身的推断**
—— 它按 `EGL_NATIVE_VISUAL_ID` 匹配后就跳过，**从未真正尝试**在该 visual 上建面。该探针保留用于枚举
config 属性（`-a`），但**不要再用它的“必然失败”结论**。

**影响**：原计划向厂商提的「EGL 需覆盖全部 visual」需求项**作废**（不需要为 EGL 重建 config↔visual
映射表）；黑窗问题回到未定位状态，需重新排查（见 §6）。

### 4.2 更正：`EGL_EXT_platform_x11` 实际存在（另一个探针假象）

`jm_egl_visual_probe` 报「`EGL_EXTENSIONS 含 EGL_EXT_platform_x11: no`」是**查询方式错误**：
该扩展位于**客户端扩展**串，必须用 `eglQueryString(EGL_NO_DISPLAY, EGL_EXTENSIONS)` 查询。实测该串为：

```
EGL_EXT_client_extensions EGL_EXT_platform_base EGL_KHR_platform_wayland EGL_EXT_platform_wayland
EGL_EXT_device_query EGL_KHR_platform_gbm EGL_KHR_platform_x11 EGL_EXT_platform_x11
```

即 `EGL_KHR_platform_x11` / `EGL_EXT_platform_x11` **均存在**。应用侧用
`eglGetPlatformDisplayEXT(EGL_PLATFORM_X11_KHR, …)` 是**可行**的。

### 4.3 反编译可行性与已摸清的库结构

三个厂商用户态库**均未 strip**（符号表完整），`objdump` / `nm` / `readelf` / `radare2` 可直接
得到函数名与数据结构，具备做二进制补丁的条件。已摸清的关键地址（库：`libEGL_mwv207.so.1.5.0`）：

| 项 | 地址/值 |
|---|---|
| `eglGetConfigs` / `eglChooseConfig` / `eglGetConfigAttrib` | `0x18e70` / `0x19038` / `0x19d70` |
| `eglCreateWindowSurface` → `veglCreatePlatformWindowSurface` | `0x20570` → `0x1fac8`（attrib 解析 @`0x1fb88`） |
| EGL config 记录步长 | **220 字节**（`display+96` 为基址，索引 1-based） |
| `EGL_NATIVE_VISUAL_ID`(0x302E) 分支 | @`0x1a0a8` —— **只传 display，不读 config** |
| `EGL_NATIVE_VISUAL_TYPE`(0x302F) 分支 | @`0x19e70` —— 读 `config+48`，存的是**位深/格式代码**（`0x10`=16bpp、`0x20`=32bpp、`0x3038`=EGL_NONE），**不是 visual id** |

另有 `libGLX_mwv207`（789 KB）与 `jmgpu_dri.so`（4.0 MB）可用于后续专项。§3.8 已给出 `jmgpu_dri.so`
的扩展表结构（`__glExtension` 206 条已满、`glGetProcAddress` 两张表的 `func` 字段文件内恒为 0）
——结论是**要新增能力必须新增代码段 + trampoline**，不能只改数据表。

### 4.4 `glEGLImageTargetTexStorageEXT`：原生驱动未实现，glvnd 空桩（反编译结论）

> 这是 §3.3 兼容层要兜的底。本轮通过反编译把"为什么需要兼容层"钉成了事实。

**实测 / 反编译证据链**：

1. 运行时 `glXGetProcAddress("glEGLImageTargetTexStorageEXT")` 返回**非 NULL**（应用能拿到函数指针），
   但它是 **glvnd `libGLdispatch.so.0` 的分发桩**（`dladdr` 解析到 `libGLdispatch.so.0+0x63b00`），
   **不在**厂商 `libGLX_mwv207.so` / `jmgpu_dri.so` 内。
2. 对厂商两个库做全符号+字符串扫描：
   - `jmgpu_dri.so` 只导出 `glEGLImageTargetTexture2DOES` / `glEGLImageTargetRenderbufferStorageOES`
     （可用 OES 路径）；**完全没有** `glEGLImageTargetTexStorageEXT` 符号，**也没有**它的函数名字符串。
   - 其 `GL_DISPATCH_TABLE` 仅 152 字节（19 个槽），不是全量分发表。
   - 结论：原生驱动**压根没实现**该扩展函数，glvnd 用空桩应答 → 调用后纹理恒全零（即 §3.6 的"绿屏/全零"）。
3. 原生栈 `glGetString(GL_EXTENSIONS)` **不广告** `GL_EXT_EGL_image_storage`（实测 `advertised = NO`）；
   该扩展与 storage 入口只在我们的兼容层（LD_PRELOAD）介入后才出现（装后 `glxinfo` 可查到）。

**结论**：

- 这不是"补一个字段/修一个判断"能解决的小补丁——要在驱动层让 storage 真正工作，得往 `jmgpu_dri.so`
  的 getproc 里注入函数名 + 重定向到 OES 实现，比在 glvnd 拦截层（兼容层）做重定向**更侵入、更脆**。
  与 §3.8「两处缺陷属未实现，无法小补丁修复」一致。
- **正确修复 = 兼容层**（系统级 LD_PRELOAD，已安装；或应用内等价拦截，purelive 已采用）。
- 对驱动侧的真正诉求：请厂商**实现** `glEGLImageTargetTexStorageEXT`（复用 OES 的 dmabuf 绑定逻辑即可），
  实现后兼容层可整体退役。

## 7. 已知限制（**请勿当成本次适配的缺陷上报**）

### 7.1 更正：「EXA 只注册了 Solid」是误判

早前记录称厂商 DDX 的 EXA 只加速 `Solid`、其余 2D 走软件。**该结论已排除**：完整读取日志后实际注册
**5 项** —— `Solid` / `Copy` / `Composite (RENDER)` / `UploadToScreen` / `DownloadFromScreen`，2D 加速是齐的。
（误判原因：日志每行都以 `[时间]` 开头，用 `sed '/Driver registered support/,/^\[/p'` 会在下一行就截断。）
同理已排除：EXA 结构体在两版 Xorg 间位移（`exa.h` 的 `ExaDriverRec` 在 1.20.4 与 21.1.16 间布局一致）。

### 7.2 GL(`gl2`) 合成不可用，当前固定用 XRender —— 代价是**没有窗口模糊特效**

同款应用 1920×1080 录屏逐帧去重实测：

| 配置 | 有效帧率 |
|---|---|
| KWin `gl2`（GL 合成）+ 内核 vblank 修复 | **≈1.2 fps**（修复前 ≈8 fps） |
| `gl2` + DDX `EnablePageFlip off` | ≈11.2 fps（最佳，仍不可用） |
| `gl2` + `EnablePageFlip off` + `TearFree off` | ≈1.4 fps（更差） |
| **XRender（CPU）合成** | **60 fps 满帧** |

结论：瓶颈在**厂商 GL 合成实现本身**（纹理上传/TFP/同步），非 DDX 页翻转策略；且与 vblank 缺陷
相互独立。工程选择 = 固定 `XRender` 合成，代价是 **KWin 的窗口模糊（blur）不可用**（blur 依赖 GL 合成）；
其余桌面特效（透明度、缩放、动画）不受影响。

### 7.3 任务栏（dde-shell）走 Mesa(CPU) 包装

任务栏是 Qt Quick 高频重绘，走厂商 GL 明显掉帧，故包装为 Mesa 渲染。
**应用侧若发现“任务栏不如其它桌面元素跟手”属预期**，非应用问题。

### 7.4 厂商驱动缺陷清单（已反馈，应用侧可据此设规避）

1. **GL 客户端垂直同步等待超时**：vblank 事件流 ≈1Hz（GPU 中断本身正常，≈266Hz）。
   → 已由内核 `drm.vblankoffdelay=0` 根治（仅本机可控，属驱动缺陷）。
2. **GL 合成路径性能异常**：`gl2` 8fps vs `XRender` 47fps，约 1/6（见 §7.2）。
3. ~~**`glEGLImageTargetTexStorageEXT` 原生驱动未实现**（厂商 `jmgpu_dri.so` 无此符号/字符串，glvnd 空桩致纹理恒全零）→ 已由 §3.3 兼容层兜底（见 §4.4，非"小补丁"可修）。~~
   → **2026-09-16 更新：已原生修复**（README §9）。系统改动见 §2 #8：给 `jmgpu_dri.so` 补上
   `GL_EXT_EGL_image_storage` 广告，并在 `libGLX_mwv207` / `libEGL_mwv207` 的别名表里把
   `glEGLImageTargetTexStorageEXT` 改写/重定向到可用的 OES 实现。实测（`x11egl` 上下文）
   `glEGLImageTargetTexStorageEXT` 与 OES 行为一致（纹理均 256x128），系统原版 mpv 无需
   `LD_PRELOAD` 即输出 `Using EGL dmabuf interop via GL_EXT_EGL_image_storage`。
   **§3.3 的 `libjm_gl_compat.so` 兼容层因此降级为可选冗余**（可退役）。
4. **reserved-mem（VRAM）分配器 `.GetSGT` 为空桩** → 标准 `map_dma_buf` 导入必然失败。
5. **解码 surface 池按“一块连续显存”申请** → 可见窗口碎片化时整组回退 CPU 不可见池。
6. **X 驱动未通过 `GLX_EXT_libglvnd` 通告 vendor 名 `mwv207`**（当前报 Xorg 默认 `mesa`）→ 见 §3.1。
