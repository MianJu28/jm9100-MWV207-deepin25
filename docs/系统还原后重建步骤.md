# 系统还原后重建完整栈的步骤

> 场景：Deepin 把系统还原（重装/恢复出厂/滚动升级回滚）后，**JM9100 所需的全部件都丢了**——
> 厂商用户态库、内核 DKMS 模块、`modprobe.d` 配置、Xorg 驱动片段、以及本仓库对 DDX 的字节补丁。
> 本文按顺序给出**可直接复制执行**的步骤，并标注每步的**验证方法**与**回退方法**。
>
> 目标状态：`jmgpu` 内核模块（本仓库构建）+ 厂商用户态闭源栈 + 专有 DDX（含 ABI 25 与
> TearFree 同步补丁），显示 / GL / VA-API 硬解全部可用。
>
> 适用机型：飞腾 D3000 + 景嘉微 JM9100（PCI `0731:9100`），内核 `6.6.155-arm64-desktop-hwe`。

## ⚡ 快捷方式：脚本化切换（2026-09-17 新增）

本文档的 §1~§8 是**手工步骤**（便于理解每一步、便于排错）。
日常**成套切换**可直接用仓库脚本，它把两套栈期望**相反**的配置统一管理：

```bash
cd ~/Desktop/Git/jm9100

sudo ./scripts/switch_stack.sh status     # 只读：看当前跑哪套栈、哪些配置不匹配
sudo ./scripts/switch_stack.sh vendor     # 切到厂商栈（= 本文档 §1~§6；需手动重启）
sudo ./scripts/switch_stack.sh system     # 切回系统自带驱动（**系统升级前**必做；需手动重启）
sudo ./scripts/switch_stack.sh backup     # 只备份
sudo ./scripts/switch_stack.sh restore    # 回到上次备份的状态
```

**三者期望相反的地方**（脚本会自动成套处理，手工做时最容易漏）：

| 配置 | 厂商栈 | 系统栈 |
|---|---|---|
| `/usr/share/X11/xorg.conf.d/10-mwv207.conf` | 需要（`MatchDriver "jmgpu"`） | **必须删除**（驱动名不符 ⇒ X 起不来） |
| `/etc/environment` 的 `__GLX_VENDOR_LIBRARY_NAME=mwv207` | 需要 | **删除**（否则 GL 走错库） |
| DKMS `mwv207` 注册 | 需要（`installed`） | **必须移除**（否则内核升级触发重编 ⇒ 中断更新） |

> **系统升级前**：`sudo ./scripts/switch_stack.sh system` → `sudo reboot` → 升级。
> 升级后若要恢复厂商栈：确认 `/usr/src/mwv207-1.7.0.uos` 存在后
> `sudo ./scripts/switch_stack.sh vendor` → `sudo reboot`。

## ⚠️ 第 0 条（最高优先级）—— 读完全文再动手

**任何会改变"开机行为"的命令，必须：先列命令 + 回退步骤 → 由操作者本人确认 → 才执行。**
**重启类操作（`reboot` / 重启 `lightdm`）一律由使用者本人执行**（在图形会话里重启 X 会直接结束会话）。

属"改变开机行为"的操作（满足任一条即是）：

| 类别 | 具体 |
|---|---|
| 写持久配置 | `/etc/modprobe.d/`、`/etc/modules-load.d/`、`/etc/initramfs-tools/`、GRUB |
| 重建 initramfs | `update-initramfs` / `mkinitramfs` / `dracut` / `grub-*` |
| 重启 | `reboot` / `shutdown` / 重启 `lightdm` 等显示管理器 |

**为什么这条排第一**：上述操作会把改动**冻结进 initramfs 或开机路径**。一旦新驱动在该内核上
跑不起来，开机时**既加载不到新驱动、又因 `blacklist` 回不到原驱动** ⇒ **黑屏，只能还原系统**。
本机已因此**两次**还原（一次是 `enable_wc=0`，一次是 `sync_dkms.sh build` 把
`blacklist mwv207` + `modules-load jmgpu` 冻结进 initramfs）。

**做任何持久化之前，先确认手边有可用的回退**：
```bash
# 官方回退（在 tty 或 SSH 里执行）：
cd ~/Desktop/Git/jm9100 && sudo ./scripts/force_mode_test.sh boot-undo && sudo reboot
```
> 若 `update-initramfs` 又崩（139，见 §1 警告），`boot-undo` 可能不干净 ⇒ 手动删配置即可：
> ```bash
> sudo rm -f /etc/modprobe.d/zz-jmgpu-test-blacklist.conf /etc/modules-load.d/jmgpu.conf
> sudo rmmod jmgpu; sudo modprobe mwv207       # 立即回到系统自带驱动
> ```

**优先用"不写持久配置"的运行时手段**做验证（不触碰 initramfs）：

```bash
# 运行时把设备强制绑到 jmgpu（重启即失效，不改任何持久配置）
echo jmgpu | sudo tee /sys/bus/pci/devices/0000:07:00.0/driver_override
sudo modprobe jmgpu
# 撤销：
echo "" | sudo tee /sys/bus/pci/devices/0000:07:00.0/driver_override
sudo rmmod jmgpu; sudo modprobe mwv207
```

## 1. 内核模块（本仓库源码 → DKMS）

本仓库源码在 `~/Desktop/Git/jm9100/kernel/`（`git` 提交 `27537d0`，76 个 `.c` / 147 个 `.h`）。

```bash
# 1.1 重建 DKMS 源码目录（还原会把它删掉）
sudo mkdir -p /usr/src/mwv207-1.7.0.uos
cd ~/Desktop/Git/jm9100/kernel
sudo cp -f *.c *.h Makefile* dkms.conf Kconfig* /usr/src/mwv207-1.7.0.uos/

# 1.2 注册 DKMS（若已注册会提示，可忽略）
sudo dkms add mwv207/1.7.0.uos

# 1.3 构建 + 安装 + 重建 initramfs + 校验（脚本自带 139 重试与 srcversion 校验）
cd ~/Desktop/Git/jm9100
sudo ./scripts/sync_dkms.sh build
```

**期望输出**：
```
==> dkms build mwv207/1.7.0.uos
==> dkms install 完成
    磁盘模块    srcversion: <指纹>
    initramfs  srcversion: <同一指纹>
==> 校验通过: initramfs 已含最新模块
```

**⚠️ 本机已知问题（非驱动问题）**：
1. **`initramfs` 校验可能失败**（`initramfs 里没有 jmgpu.ko`）—— 属**误报**：
   本系统 initramfs **从设计上不收录 `updates/`（DKMS）目录**下的模块（实测 `updates/*.ko` = 0 个，
   而 `kernel/drivers/*.ko` = 1636 个）。这类模块由 **rootfs 阶段的 udev modalias** 加载。
   ⇒ **校验失败不代表安装失败**，只要 `磁盘模块 srcversion` 有值即可。
2. **`update-initramfs` 偶发 139 段错误** —— 根因是 `deepin-anything` 的 **`vfs_monitor.ko`**
   在内核 `6.6.155` 上触发内核 `BUG()`（`brk #6`，指令 `d42000c0`，`Tainted: G D W OE`），
   表现为 `cp` 随机 SIGSEGV、`update-initramfs` 失败。诊断与证据见 `README.md` §13.6。
   临时规避：
   ```bash
   sudo rmmod vfs_monitor        # 之后 cp / update-initramfs 立即恢复正常（实测 100 次复制 0 失败）
   # 持久规避（代价：deepin 文件索引/全局搜索失效）：
   echo 'blacklist vfs_monitor' | sudo tee /etc/modprobe.d/blacklist-vfs-monitor.conf
   ```

**验证**：
```bash
lsmod | grep jmgpu
cat /sys/module/jmgpu/srcversion          # 应等于磁盘模块的 srcversion
ls /dev/jmgpu                             # jmgpu 私有节点（WA/2D 用）
ls /dev/dri/                              # card0 + renderD128
```

**⚠️ 必查：`dkms status` 必须是 `installed`，不能只是 `added`**

```bash
dkms status | grep -i mwv207
#   mwv207/1.7.0.uos, 6.6.155-…, aarch64: installed   ← 正确
#   mwv207/1.7.0.uos: added                            ← **错误**：模块文件不在 /lib/modules 下
```

区别与后果：

| 状态 | `/lib/modules/$(uname -r)/updates/dkms/jmgpu.ko` | 后果 |
|---|---|---|
| `installed` | 存在 | 开机 `modules-load` 能加载 |
| **`added`** | **不存在**（只有 `/var/lib/dkms/.../build/` 里的 `.o`） | 开机 `modules-load jmgpu` **找不到文件** ⇒ **无驱动** ⇒ X 回落 `modesetting`/`fbdev` |

> 出现 `added` 的常见原因：内核升级后 DKMS 未对新内核 `install`；或 `dkms remove` 只删了安装、
> 留下注册。修复：重跑 `sudo ./scripts/sync_dkms.sh build`（= build + install + update-initramfs），
> 再确认 `dkms status` 变回 `installed` 且模块文件存在。

**回退**：
```bash
sudo dkms remove mwv207/1.7.0.uos --all
```

## 3. `libdrm.so.2.4.0` 兼容链接（**关键、易漏**）

DDX 的 `NEEDED` 里写的是旧式 soname **`libdrm.so.2.4.0`**，而现代 `libdrm2` 包只提供
`libdrm.so.2 -> libdrm.so.2.<新版本号>`。缺失时 X 报：

```
(EE) Failed to load /usr/lib/xorg/modules/drivers/mwv207_drv.so:
     libdrm.so.2.4.0: cannot open shared object file: No such file or directory
```

**修法**（**两个位置都要建**，缺一不可）：
```bash
# ① 系统库目录：给"无 RUNPATH"的库用（libGLX_mwv207 / libEGL_mwv207 / jmgpu_dri.so）
sudo ln -sf /usr/lib/aarch64-linux-gnu/libdrm.so.2 \
            /usr/lib/aarch64-linux-gnu/libdrm.so.2.4.0
# ② DDX 的 RUNPATH 目录（mwv207_drv.so 的 RUNPATH 指向这里）
sudo ln -sf /usr/lib/aarch64-linux-gnu/libdrm.so.2 \
            /usr/lib/aarch64-linux-gnu/mwv207/libdrm.so.2.4.0

# 验证：四个厂商库都不应再有 "not found"
for f in /usr/lib/aarch64-linux-gnu/mwv207/libGLX_mwv207.so.1.2.0 \
         /usr/lib/aarch64-linux-gnu/mwv207/libEGL_mwv207.so.1.5.0 \
         /usr/lib/aarch64-linux-gnu/dri/jmgpu_dri.so \
         /usr/lib/xorg/modules/drivers/mwv207_drv.so; do
  printf "%-56s " "$(basename $f)"
  ldd "$f" 2>&1 | grep -q 'not found' && ldd "$f" 2>&1 | grep 'not found' || echo OK
done
```

> **⚠️ 为什么必须两处都建**（2026-09-17 踩坑记录）：
> 只有 `mwv207_drv.so` 带 `RUNPATH=/usr/lib/aarch64-linux-gnu/mwv207`；
> **`libGLX_mwv207.so` / `libEGL_mwv207.so` / `jmgpu_dri.so` 三个库都没有 RUNPATH**，
> 只能按系统默认路径查找。若只在 `mwv207/` 目录建链接，这三个库会 `not found`，
> 后果是 **GL 静默回落到 Mesa/llvmpipe**（`glxinfo` 显示 `llvmpipe` 而非 `Jingjia JM9100`），
> 日志表现为 `glx: failed to create dri3 screen` + `failed to load driver: jmgpu`。
> 建到系统目录后 `OpenGL renderer string: Jingjia JM9100` 立即恢复。

> 原理：`drmModePageFlip` / `AddFB` / `RmFB` / `GetResources` 等 API 自 libdrm 2.4.x 起
> **签名未变**，用新版 libdrm 提供的实现是安全的。

**回退**：`sudo rm /usr/lib/aarch64-linux-gnu/{,mwv207/}libdrm.so.2.4.0`

## 4. Xorg 配置（让 X 用厂商 DDX）

```bash
sudo tee /usr/share/X11/xorg.conf.d/10-mwv207.conf >/dev/null <<'EOF'
Section "OutputClass"
        Identifier "JMgpu"
        MatchDriver "jmgpu"
        Driver "mwv207"
EndSection
EOF
```

> `MatchDriver "jmgpu"` 对应**内核驱动名**（`/sys/bus/pci/devices/0000:07:00.0/driver -> .../drivers/jmgpu`），
> `Driver "mwv207"` 对应**X 驱动**（`mwv207_drv.so`）。

**注意**：一个 PCI 设备**只能绑定一个内核驱动**（`jmgpu` 与发行版自带 `mwv207` 互斥）。
若发行版自带 `mwv207` 被自动加载，需确保 `jmgpu` 先绑定（可用本仓库
`scripts/switch_full_closed_stack.sh`，它会用 `driver_override` 强制绑定，失败自动回退）。

**回退**：删除该文件 + 重启 lightdm。

## 5. DDX 字节补丁：ABI 24 → 25（**必做**）

Xorg 1.21.1.16 要求 `ABI_VIDEODRV_VERSION 25`，厂商 DDX 按 24 编译 ⇒ 加载失败：

```
(EE) mwv207: module ABI major version (24) doesn't match the server's version (25)
(EE) Failed to load module "mwv207" (module requirement mismatch, 0)
```

仓库已有脚本（只改 4 字节：`XF86ModuleVersionInfo.abiversion`，`.data` 偏移 `0x217f8`）：

```bash
cd ~/Desktop/Git/jm9100

# 5.1 先备份当前 DDX（原件/当前版本都留一份）
sudo cp -a /usr/lib/xorg/modules/drivers/mwv207_drv.so \
   /persistent/home/admin/jm9100-xdrv-backup/mwv207_drv.so.$(date +%F-%H%M).bak

# 5.2 打补丁（脚本自带：modname 校验 + abiclass 校验 + 自检）

        /tmp/mwv207_drv.so.abi25 --abi 25

# 5.3 安装
sudo cp /tmp/mwv207_drv.so.abi25 /usr/lib/xorg/modules/drivers/mwv207_drv.so

# 5.4 验证
```

## 6. DDX 字节补丁：TearFree 2D 同步（**修复三角错位，可选**）

**问题**（`README.md` §12/§13）：视频窗口出现**三角/楔形错位 + 重复之前片段**。
A/B 定位：`Option "TearFree" "off"` 后明显减少 ⇒ 主因是 DDX 的"合成 → 扫描缓冲"拷贝
（`drm_jmgpu_bo_xfer_to_dev`，即内核 `DRM_JM_GEM_XFER_RECT`）**提交后立即返回、不等 2D 写完**。

**反编译证据**（BuildID `912c7bd4bf721ea7c5b6ca44690b0c596500e6bf`）：
- 上传例程 1：`0x12ca4 bl xfer_to_dev` → `0x12cac cbnz` → `0x12cb0 ldp x29,x30,[sp,#16]` → `ret`（**无同步**）
- 上传例程 2：`0x131f0 bl xfer_to_dev` → `0x131f8 cbnz` → `0x131fc ldp x29,x30,[sp,#16]` → `ret`（同上）
- 驱动里**已存在**"等 2D 空闲"封装 **`0x10d78`**，却**全库 0 引用**（定义了从未调用）

**补丁（2 处、各 1 条指令，无需跳板）**：
```
0x12cb0:  ldp x29, x30, [sp, #16]   ->   bl 0x10d78
0x131fc:  ldp x29, x30, [sp, #16]   ->   bl 0x10d78
```
正确性：`bl` 把返回地址写入 `x30`，紧跟的原指令从栈恢复**真正**的 LR ⇒ 原逻辑不变；
`0x12cb0` 有 3 处跳转、`0x131fc` 有 1 处跳转指向它 ⇒ **所有返回路径都覆盖**。

```bash
cd ~/Desktop/Git/jm9100

# 6.1 预检（校验原件指纹 + 插入点指令确实匹配）
python3 tools/patch_ddx_tearfree_sync.py /usr/lib/xorg/modules/drivers/mwv207_drv.so --check

# 6.2 生成补丁版（只对副本操作，脚本不改输入文件）
python3 tools/patch_ddx_tearfree_sync.py /usr/lib/xorg/modules/drivers/mwv207_drv.so \
        /tmp/mwv207_drv.so.tearfree-sync

# 6.3 确认差异恰好 8 字节
cmp -l /usr/lib/xorg/modules/drivers/mwv207_drv.so /tmp/mwv207_drv.so.tearfree-sync | wc -l

# 6.4 安装
sudo cp /tmp/mwv207_drv.so.tearfree-sync /usr/lib/xorg/modules/drivers/mwv207_drv.so
```

> **与 §5 叠加**：两者改的位置不同（ABI 在 `.data 0x217f8`，本补丁在 `.text`），可先后打、互不冲突。

## 7.9 本次（2026-09-17）踩坑实录

重建过程中实际踩到的坑，**按代价从大到小**排列。每条都给出**症状 → 根因 → 判据 → 修正**。

### 坑 1（代价最大）：`libdrm.so.2.4.0` 只建了一处 ⇒ GL 静默回落软件栈

| 项 | 内容 |
|---|---|
| **症状** | `glxinfo` 显示 `llvmpipe (Mesa)`、`glxgears` 仅 **478 FPS**；日志只有两行模糊提示：`glx: failed to create dri3 screen` / `failed to load driver: jmgpu`（**看起来像驱动坏了**） |
| **误判** | 先怀疑 glstorage 补丁、`__driDriverExtensions` 符号、glvnd vendor 配置…… **全部方向错误** |
| **根因** | `libdrm.so.2.4.0` 只建在 **DDX 的 RUNPATH 目录** `.../mwv207/`；而 **`libGLX_mwv207` / `libEGL_mwv207` / `jmgpu_dri.so` 三个库没有 RUNPATH**，按系统默认路径查找 ⇒ `not found` ⇒ 厂商 GLX 加载失败 ⇒ glvnd 回落 Mesa |
| **判据** | 四个库逐个 `ldd` 看 `not found`（见 §3） |
| **修正** | `ln -sf libdrm.so.2 /usr/lib/aarch64-linux-gnu/libdrm.so.2.4.0`（**系统目录也必须建**） |
| **效果** | `renderer: Jingjia JM9100`；**478 → 17,000 FPS（约 35 倍）** |

> **教训**：`ldd <库> | grep 'not found'` 是"厂商库加载失败"的**第一判据**，比看日志快得多。
> 本次四个库中三个都缺同一依赖，日志却只给两行模糊信息。

### 坑 2：`DISPLAY` 拿错（`:0` vs `:1`）⇒ 误判"命令无输出"

| 项 | 内容 |
|---|---|
| **症状** | `DISPLAY=:0 glxinfo -B \| grep renderer` **无任何输出**（被 grep 吞掉错误），看起来像"命令跑了但没结果" |
| **根因** | 本机 **lightdm/Xorg 起在 `:1`**（`Xorg :1 -seat seat0`），`:0` 不存在 ⇒ `unable to open display` |
| **判据** | `tr '\0' '\n' < /proc/$(pgrep -x kwin_x11\|head -1)/environ \| grep DISPLAY` |
| **修正** | 全部测试命令改用取到的 `DISPLAY`（本机 `:1`） |

> **教训**：**不要假设 `:0`**。任何 X 测试前先取当前会话的 `DISPLAY`。
> 另外：`grep` 吞错误输出会制造"静默失败"的假象，排查时应**先看原始输出**再过滤。

### 坑 3：`vfs_monitor`（deepin-anything）导致 `cp` 随机 SIGSEGV(139)

| 项 | 内容 |
|---|---|
| **症状** | `update-initramfs` 失败：`dracut-install: ERROR: 'cp ...' failed with 139`；内核日志有 `note: cp[..] exited with irqs disabled` / `exited with preempt_count 1` |
| **误判** | 曾归因于"新装的内核模块"或"`compression`/`fastClear` 参数组合"（**结论已撤回**） |
| **根因** | `deepin-anything` 的 **`vfs_monitor.ko`**（挂钩 VFS）在 6.6 内核上触发内核 **`BUG()`**（ARM64 `brk #6`，指令 `d42000c0`，`Tainted: G D W OE`）；崩溃目标随机（`i2c-nforce2.ko`/`hix5hd2_gmac.ko`/`reset-uniphier-glue.ko` 等） |
| **判据** | `sudo dmesg \| grep -iE 'BRK handler\|preempt_count\|irqs disabled'`；或批量复现 `cp` |
| **修正** | `sudo rmmod vfs_monitor`（立即见效）→ 之后 100 次复制 **0 失败**、`update-initramfs` **rc=0** |
| **持久规避** | `echo 'blacklist vfs_monitor' \| sudo tee /etc/modprobe.d/blacklist-vfs-monitor.conf`（代价：deepin 文件索引/全局搜索失效） |

> **验证记录**：卸载前 `update-initramfs` 稳定 139；卸载后 **rc=0**，且 `BRK handler` 计数停止增长。

### 坑 4：DDX 补丁**只打 ABI、漏打布局** ⇒ 后续 `NULL+0x48` 段错误

| 项 | 内容 |
|---|---|
| **根因** | Xorg 1.21 删除了 `xf86str.h` 的 `Bool flipPixels` ⇒ `ScrnInfoRec` 其后字段整体 **−8 字节** ⇒ 回调槽错位，`xf86DeleteScreen` 误调 LeaveVT，读未初始化的 `pScrn->pScreen` |
| **修正** | 必须用 **`build-cli/mwv207_drv.so.abi25.fixed3`**（**ABI + 布局双补丁**，md5 `297aee83b5db3a3bccf33ff7ac2698fc`），**不要**只跑 `tools/patch_xorg_abi.py` |
| **判据** | `md5sum /usr/lib/xorg/modules/drivers/mwv207_drv.so` 应等于 `297aee83…` |

### 坑 5：initramfs **不收录 `updates/` 目录** ⇒ `sync_dkms.sh` 的"校验失败"是**误报**

| 项 | 内容 |
|---|---|
| **症状** | `sync_dkms.sh build` 报 `!! 校验失败: initramfs 里的 jmgpu.ko 与磁盘不一致` |
| **实测** | 本系统 initramfs 内 `updates/*.ko` = **0 个**，`kernel/drivers/*.ko` = **1636 个**；`modules.dep` 中既无 `jmgpu` 也无 `vfs_monitor` |
| **结论** | 该系统的 initramfs **设计上就不收录 DKMS 模块**，DKMS 模块由 **rootfs 阶段的 udev modalias** 加载 ⇒ **校验失败 ≠ 安装失败**，只需确认 `dkms status` 为 `installed` 且磁盘模块存在 |

### 坑 6：`dkms status` 只到 `added`（未 `install`）⇒ 开机加载不到模块

| 项 | 内容 |
|---|---|
| **症状** | 开机后无 `/dev/jmgpu`、无 `/dev/dri/card0`；X 回落 `modesetting`/`fbdev`；`uos-trace: No drm device, wait 1999 times; timeout` |
| **根因** | `modules-load` 想加载 `jmgpu` 但 `/lib/modules/$(uname -r)/updates/dkms/jmgpu.ko` **不存在**（DKMS 只 `added`、未 `install`；常见于内核升级后） |
| **判据** | `dkms status \| grep mwv207` 必须是 **`installed`**（见 §1） |
| **修正** | 重跑 `sudo ./scripts/sync_dkms.sh build`，再确认状态为 `installed` |

### 坑 7（**最危险**）：过早把 `blacklist mwv207` + `modules-load jmgpu` 冻结进 initramfs ⇒ **黑屏**

| 项 | 内容 |
|---|---|
| **症状** | 重启后**黑屏**，只能还原系统（本机已因此**两次**还原） |
| **根因** | 在 `jmgpu` 显示管线**尚未在本内核上验证可用**时，就执行了 `sync_dkms.sh build`（内含 `update-initramfs -u`），把"**屏蔽原驱动 + 强制加载新驱动**"写进 initramfs。一旦新驱动起不来，开机时**既加载不到新驱动、又回不到原驱动** |
| **正确顺序** | ① 先只装模块（不改持久配置）→ ② 用 **运行时 `driver_override`** 验证 → ③ 确认 `glxinfo` 走硬件、桌面正常 → ④ **最后**才做持久化，且**手边先备好回退命令** |
| **运行时验证法**（不碰 initramfs） | 见本文档"第 0 条"里的 `driver_override` 片段 |
| **回退** | `sudo ./scripts/force_mode_test.sh boot-undo && sudo reboot`；紧急时手动删 `/etc/modprobe.d/zz-jmgpu-test-blacklist.conf` + `/etc/modules-load.d/jmgpu.conf` 并 `rmmod jmgpu; modprobe mwv207` |

### 坑 8：`dde-shell`（任务栏）**必须走 Mesa/CPU**，与厂商 GL 是否修好**无关**

| 项 | 内容 |
|---|---|
| **现象** | 驱动修好后（`glxgears` 1.7 万 FPS）**撤销** `fix_dock_mesa.sh` 包装 ⇒ 任务栏**又卡** |
| **根因** | 厂商 GL 在 **dde-shell 这类高频重绘 UI** 上依然慢（文档 §8.2 记录：厂商 GL 合成 `gl2` 仅 **1–11 fps**，而 CPU 路径 **47 fps**） |
| **结论** | 两件事**互不替代**：**GL 应用**吃硬件加速（1.7 万 FPS）；**任务栏**刻意走 CPU（`fix_dock_mesa.sh` 包装，带 `dde-shell.real` 备份） |
| **判据** | `pgrep -af dde-shell` 应看到 **`/usr/bin/dde-shell.real`**（走包装）；`/usr/bin/dde-shell` 应是 ~486 字节的 `sh` 脚本 |
| **回退/恢复** | `sudo bash ~/fix_dock_mesa.sh`（应用）/ `... revert`（还原） |

> **重要**：不要把"任务栏流畅"当成"驱动修好了"的证据 —— 它走的是**另一条路径**。

**三条最贵的坑（详见 §7.9）**：

1. **`libdrm.so.2.4.0` 只建一处 ⇒ GL 静默回落 llvmpipe**（478 → 17,000 FPS 的差别）；
   `libGLX_mwv207`/`libEGL_mwv207`/`jmgpu_dri.so` **无 RUNPATH**，必须建在**系统目录**。
2. **`DISPLAY` 拿错**（本机 `:1`/`:3`/`:4` 都出现过）⇒ 测试"看似无输出" ⇒ 险些误判 GL 已坏。
3. **过早持久化 ⇒ 黑屏**（本机已两次还原）：`blacklist` + `modules-load` + `update-initramfs`
   必须在"驱动已实测可用 + 回退在手"后才做。

**第四条坑（2026-09-17 下午，代价很大）—— 勿改 `libglx.so`**：

为"不依赖环境变量"而把 `/usr/lib/xorg/modules/extensions/libglx.so` 的默认 GLX vendor
从 `"mesa"` 改成 `"mwv207"`，结果 **打补丁后 6 秒**出现：

```
[CRTC:35:crtc_0] vblank wait timed out
drm_atomic_helper_wait_for_vblanks … j9_handle_j9m_principium+0x9c/0xc0 [jmgpu]
jmgpu: *ERROR* flip_done timed out / commit wait timed out
Code: d42000c0 (d42000c0)                      ← ARM64 brk #6 = BUG()
Fixing recursive fault but reboot is needed!   ← 内核状态损坏
```

**症状**：EasyTier 图标一闪而过无窗口、`MiniBrowser` 段错误、`cp` 随机 139
（**多个不相关程序同时异常** ⇒ 一定是内核/驱动层）。
**回退后**：vblank 超时 3 → **0**，全部恢复。

**两个错误**：

1. **改错了库** —— `libglx.so` 是 **Xorg 模块**（server 侧）；
   客户端走的是 **glvnd**（`libGLX.so.0`），而后者**内部没有默认 vendor 字符串**
   （实测 `mesa@[]`，vendor 名运行时从 X server 取）⇒ **改 Xorg 模块对客户端毫无作用**。
2. **"更彻底"≠更好** —— 改 server 侧 vendor 会打乱 DDX ↔ 内核驱动的既有协作，触发 vblank 路径失效。

**正确做法**：保持 `libglx.so` **原版**，变量只写 `/etc/environment`。

**取证捷径**：见到"多个不相关程序同时异常"时先查内核：

```bash
sudo dmesg | grep -E 'vblank wait timed out|commit wait timed out|BUG:|recursive fault'
```

**两条系统级坑（与本仓库驱动无关）**：

- **`vfs_monitor`（deepin-anything）** 导致 `cp`/`update-initramfs` 随机 139（内核 `BUG()`）；
  `sudo rmmod vfs_monitor` 即恢复（详见 §1 与 §7.9 坑 3）。
- **initramfs 不收录 `updates/` 目录** ⇒ `sync_dkms.sh` 的"initramfs 校验失败"是**误报**。

**一条易搞错的认知**：

- **任务栏（`dde-shell`）流畅 ≠ 驱动修好** —— 它走 `fix_dock_mesa.sh` 包装，**刻意**用 Mesa/CPU
  （厂商 GL 在它上面只有 1–11 fps）。撤销包装后**又会卡**（2026-09-17 实测）。
