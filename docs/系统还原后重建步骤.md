# 系统还原后重建完整栈的步骤

> 场景：Deepin 把系统还原（重装/恢复出厂/滚动升级回滚）后，**JM9100 所需的全部件都丢了**——
> 厂商用户态库、内核 DKMS 模块、`modprobe.d` 配置、Xorg 驱动片段、以及本仓库对 DDX 的字节补丁。
> 本文按顺序给出**可直接复制执行**的步骤，并标注每步的**验证方法**与**回退方法**。
>
> 目标状态：`jmgpu` 内核模块（本仓库构建）+ 厂商用户态闭源栈 + 专有 DDX（含 ABI 25 与
> TearFree 同步补丁），显示 / GL / VA-API 硬解全部可用。
>
> 适用机型：飞腾 D3000 + 景嘉微 JM9100（PCI `0731:9100`），内核 `6.6.155-arm64-desktop-hwe`。

## ⚠️ 第 0 条（最高优先级）—— 读完全文再动手

**任何会改变"开机行为"的命令，必须：先列命令 + 回退步骤 → 由操作者本人确认 → 才执行。**
**重启类操作（`reboot` / 重启 `lightdm`）一律由使用者本人执行**（在图形会话里重启 X 会直接结束会话）。

属"改变开机行为"的操作（满足任一条即是）：

| 类别 | 具体 |
|---|---|
| 写持久配置 | `/etc/modprobe.d/`、`/etc/modules-load.d/`、`/etc/initramfs-tools/`、GRUB |
| 重建 initramfs | `update-initramfs` / `mkinitramfs` / `dracut` / `grub-*` |
| 重启 | `reboot` / `shutdown` / 重启 `lightdm` 等显示管理器 |

**为什么这条排第一**：上述操作会把改动**冻结进 initramfs 或开机路径**。一旦新驱动在该内核上
跑不起来，开机时**既加载不到新驱动、又因 `blacklist` 回不到原驱动** ⇒ **黑屏，只能还原系统**。
本机已因此**两次**还原（一次是 `enable_wc=0`，一次是 `sync_dkms.sh build` 把
`blacklist mwv207` + `modules-load jmgpu` 冻结进 initramfs）。

**做任何持久化之前，先确认手边有可用的回退**：
```bash
# 官方回退（在 tty 或 SSH 里执行）：
cd ~/Desktop/Git/jm9100 && sudo ./scripts/force_mode_test.sh boot-undo && sudo reboot
```
> 若 `update-initramfs` 又崩（139，见 §1 警告），`boot-undo` 可能不干净 ⇒ 手动删配置即可：
> ```bash
> sudo rm -f /etc/modprobe.d/zz-jmgpu-test-blacklist.conf /etc/modules-load.d/jmgpu.conf
> sudo rmmod jmgpu; sudo modprobe mwv207       # 立即回到系统自带驱动
> ```

**优先用"不写持久配置"的运行时手段**做验证（不触碰 initramfs）：

```bash
# 运行时把设备强制绑到 jmgpu（重启即失效，不改任何持久配置）
echo jmgpu | sudo tee /sys/bus/pci/devices/0000:07:00.0/driver_override
sudo modprobe jmgpu
# 撤销：
echo "" | sudo tee /sys/bus/pci/devices/0000:07:00.0/driver_override
sudo rmmod jmgpu; sudo modprobe mwv207
```

## 1. 内核模块（本仓库源码 → DKMS）

本仓库源码在 `~/Desktop/Git/jm9100/kernel/`（`git` 提交 `27537d0`，76 个 `.c` / 147 个 `.h`）。

```bash

sudo cp -f *.c *.h Makefile* dkms.conf Kconfig* /usr/src/mwv207-1.7.0.uos/

# 1.2 注册 DKMS（若已注册会提示，可忽略）
sudo dkms add mwv207/1.7.0.uos

# 1.3 构建 + 安装 + 重建 initramfs + 校验（脚本自带 139 重试与 srcversion 校验）
cd ~/Desktop/Git/jm9100
sudo ./scripts/sync_dkms.sh build
```

**期望输出**：
```
==> dkms build mwv207/1.7.0.uos
==> dkms install 完成
    磁盘模块    srcversion: <指纹>
    initramfs  srcversion: <同一指纹>
==> 校验通过: initramfs 已含最新模块
```

**⚠️ 本机已知问题（非驱动问题）**：
1. **`initramfs` 校验可能失败**（`initramfs 里没有 jmgpu.ko`）—— 属**误报**：
   本系统 initramfs **从设计上不收录 `updates/`（DKMS）目录**下的模块（实测 `updates/*.ko` = 0 个，
   而 `kernel/drivers/*.ko` = 1636 个）。这类模块由 **rootfs 阶段的 udev modalias** 加载。
   ⇒ **校验失败不代表安装失败**，只要 `磁盘模块 srcversion` 有值即可。
2. **`update-initramfs` 偶发 139 段错误** —— 根因是 `deepin-anything` 的 **`vfs_monitor.ko`**
   在内核 `6.6.155` 上触发内核 `BUG()`（`brk #6`，指令 `d42000c0`，`Tainted: G D W OE`），
   表现为 `cp` 随机 SIGSEGV、`update-initramfs` 失败。诊断与证据见 `README.md` §13.6。
   临时规避：
   ```bash
   sudo rmmod vfs_monitor        # 之后 cp / update-initramfs 立即恢复正常（实测 100 次复制 0 失败）
   # 持久规避（代价：deepin 文件索引/全局搜索失效）：
   echo 'blacklist vfs_monitor' | sudo tee /etc/modprobe.d/blacklist-vfs-monitor.conf
   ```

**验证**：
```bash
lsmod | grep jmgpu
cat /sys/module/jmgpu/srcversion          # 应等于磁盘模块的 srcversion
ls /dev/jmgpu                             # jmgpu 私有节点（WA/2D 用）
ls /dev/dri/                              # card0 + renderD128
```

**⚠️ 必查：`dkms status` 必须是 `installed`，不能只是 `added`**

```bash
dkms status | grep -i mwv207
#   mwv207/1.7.0.uos, 6.6.155-…, aarch64: installed   ← 正确
#   mwv207/1.7.0.uos: added                            ← **错误**：模块文件不在 /lib/modules 下
```

区别与后果：

| 状态 | `/lib/modules/$(uname -r)/updates/dkms/jmgpu.ko` | 后果 |
|---|---|---|
| `installed` | 存在 | 开机 `modules-load` 能加载 |
| **`added`** | **不存在**（只有 `/var/lib/dkms/.../build/` 里的 `.o`） | 开机 `modules-load jmgpu` **找不到文件** ⇒ **无驱动** ⇒ X 回落 `modesetting`/`fbdev` |

> 出现 `added` 的常见原因：内核升级后 DKMS 未对新内核 `install`；或 `dkms remove` 只删了安装、
> 留下注册。修复：重跑 `sudo ./scripts/sync_dkms.sh build`（= build + install + update-initramfs），
> 再确认 `dkms status` 变回 `installed` 且模块文件存在。

**回退**：
```bash
sudo dkms remove mwv207/1.7.0.uos --all
```

## 3. `libdrm.so.2.4.0` 兼容链接（**关键、易漏**）

DDX 的 `NEEDED` 里写的是旧式 soname **`libdrm.so.2.4.0`**，而现代 `libdrm2` 包只提供
`libdrm.so.2 -> libdrm.so.2.<新版本号>`。缺失时 X 报：

```
(EE) Failed to load /usr/lib/xorg/modules/drivers/mwv207_drv.so:
     libdrm.so.2.4.0: cannot open shared object file: No such file or directory
```

**修法**（只影响 DDX 的 RUNPATH 目录，不动系统 libdrm）：
```bash
sudo ln -sf /usr/lib/aarch64-linux-gnu/libdrm.so.2 \
            /usr/lib/aarch64-linux-gnu/mwv207/libdrm.so.2.4.0

# 验证：不应再有 "not found"
ldd /usr/lib/xorg/modules/drivers/mwv207_drv.so | grep -E 'not found|drm'
```
> 原理：`drmModePageFlip` / `AddFB` / `RmFB` / `GetResources` 等 API 自 libdrm 2.4.x 起
> **签名未变**，用新版 libdrm 提供的实现是安全的。

**回退**：`sudo rm /usr/lib/aarch64-linux-gnu/mwv207/libdrm.so.2.4.0`

## 4. Xorg 配置（让 X 用厂商 DDX）

```bash
sudo tee /usr/share/X11/xorg.conf.d/10-mwv207.conf >/dev/null <<'EOF'
Section "OutputClass"
        Identifier "JMgpu"
        MatchDriver "jmgpu"
        Driver "mwv207"
EndSection
EOF
```

> `MatchDriver "jmgpu"` 对应**内核驱动名**（`/sys/bus/pci/devices/0000:07:00.0/driver -> .../drivers/jmgpu`），
> `Driver "mwv207"` 对应**X 驱动**（`mwv207_drv.so`）。

**注意**：一个 PCI 设备**只能绑定一个内核驱动**（`jmgpu` 与发行版自带 `mwv207` 互斥）。
若发行版自带 `mwv207` 被自动加载，需确保 `jmgpu` 先绑定（可用本仓库
`scripts/switch_full_closed_stack.sh`，它会用 `driver_override` 强制绑定，失败自动回退）。

**回退**：删除该文件 + 重启 lightdm。

```

(EE) Failed to load module "mwv207" (module requirement mismatch, 0)
```

仓库已有脚本（只改 4 字节：`XF86ModuleVersionInfo.abiversion`，`.data` 偏移 `0x217f8`）：


## 6. DDX 字节补丁：TearFree 2D 同步（**修复三角错位，可选**）

**问题**（`README.md` §12/§13）：视频窗口出现**三角/楔形错位 + 重复之前片段**。
A/B 定位：`Option "TearFree" "off"` 后明显减少 ⇒ 主因是 DDX 的"合成 → 扫描缓冲"拷贝
（`drm_jmgpu_bo_xfer_to_dev`，即内核 `DRM_JM_GEM_XFER_RECT`）**提交后立即返回、不等 2D 写完**。

**反编译证据**（BuildID `912c7bd4bf721ea7c5b6ca44690b0c596500e6bf`）：
- 上传例程 1：`0x12ca4 bl xfer_to_dev` → `0x12cac cbnz` → `0x12cb0 ldp x29,x30,[sp,#16]` → `ret`（**无同步**）
- 上传例程 2：`0x131f0 bl xfer_to_dev` → `0x131f8 cbnz` → `0x131fc ldp x29,x30,[sp,#16]` → `ret`（同上）
- 驱动里**已存在**"等 2D 空闲"封装 **`0x10d78`**，却**全库 0 引用**（定义了从未调用）

**补丁（2 处、各 1 条指令，无需跳板）**：
```
0x12cb0:  ldp x29, x30, [sp, #16]   ->   bl 0x10d78
0x131fc:  ldp x29, x30, [sp, #16]   ->   bl 0x10d78
```
正确性：`bl` 把返回地址写入 `x30`，紧跟的原指令从栈恢复**真正**的 LR ⇒ 原逻辑不变；
`0x12cb0` 有 3 处跳转、`0x131fc` 有 1 处跳转指向它 ⇒ **所有返回路径都覆盖**。

```bash
cd ~/Desktop/Git/jm9100

# 6.1 预检（校验原件指纹 + 插入点指令确实匹配）
python3 tools/patch_ddx_tearfree_sync.py /usr/lib/xorg/modules/drivers/mwv207_drv.so --check

# 6.2 生成补丁版（只对副本操作，脚本不改输入文件）
python3 tools/patch_ddx_tearfree_sync.py /usr/lib/xorg/modules/drivers/mwv207_drv.so \
        /tmp/mwv207_drv.so.tearfree-sync

# 6.3 确认差异恰好 8 字节
cmp -l /usr/lib/xorg/modules/drivers/mwv207_drv.so /tmp/mwv207_drv.so.tearfree-sync | wc -l

# 6.4 安装
sudo cp /tmp/mwv207_drv.so.tearfree-sync /usr/lib/xorg/modules/drivers/mwv207_drv.so
```

> **与 §5 叠加**：两者改的位置不同（ABI 在 `.data 0x217f8`，本补丁在 `.text`），可先后打、互不冲突。
